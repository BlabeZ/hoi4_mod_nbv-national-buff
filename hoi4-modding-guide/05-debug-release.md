# 05 调试、兼容与发布

## 1. 建立能解释结果的测试环境

先用目标版本原版运行一次，保留基线日志，再只启用本模组测试。这样能区分本次改动和原版本来就存在的日志噪声。记录国家、开局日期、DLC、语言、playset、模组版本、checksum 和复现步骤。

开发时使用 `-debug`；它能扩大错误记录，并支持部分文件更新后的重载。但它也改变运行行为、性能和某些地图错误的处理，发布前还必须做普通启动验收。[Wiki Debug mode](https://hoi4.paradoxwikis.com/Modding#Debug_mode)

## 2. 日志与症状排查

日志通常在用户数据目录的 `logs/`；不要误到游戏安装目录寻找。重点看 `error.log`、`game.log` 和必要时的 `system.log`。脚本 `log = "..."` 可写诊断消息，建议加项目固定前缀。[Wiki 日志说明](https://hoi4.paradoxwikis.com/Modding#Logs)

| 症状 | 先检查 | 再检查 |
|---|---|---|
| 模组完全无效果 | playset 是否启用、外部 `.mod` 的 `path`、根目录层级 | 同名本地/订阅模组、路径字符、加载冲突 |
| 启动器有版本警告 | `supported_version` 与真实版本 | 先测兼容再改元数据，不能只消掉警告 |
| 显示原始 key | 当前语言、文件后缀、首行语言、BOM | key 拼写、引号、文件是否被覆盖 |
| 事件能打开但奖励不对 | effect 所在块、country/state scope、条件是否为真 | 重复 flag、事件调用者、后续效果是否反向覆盖 |
| 国策/决议看不到 | 对象是否加载、国家选择、category、visible/available | ID 冲突、DLC 条件、脚本错误、UI |
| 图片缺失或粉色 | sprite 定义、纹理路径、大小写、实际格式 | 重复 GFX 名、资源加载顺序、缓存 |
| 启动崩溃 | 最近改动、首个有关报错、括号与引用 | 地图、装备原型、人物角色、替换目录是否缺必要数据 |
| 编辑器大量报错 | vanilla 路径、游戏识别、缓存、规则版本 | 上游已知误报，再与运行结果比对 |
| 换电脑才出问题 | 漏打包文件、绝对路径、依赖和大小写 | 用户目录残留、DLC、平台差异 |

不要把“删除全部 mod、数据库、订阅”作为第一步。官方帮助页确有重建启动器状态的排查方案，但这属于加载故障的后续处理，先保存文件与 playset 信息并理解影响，再有针对性操作。本次未执行任何此类删除。[官方帮助页](https://support.paradoxplaza.com/hc/en-us/articles/360019724999-Mods-won-t-load-Mod-load-order-failed)

## 3. 常用调试入口

| 入口 | 用途 | 注意 |
|---|---|---|
| `event h4guide.1` | 执行教学事件 | 强制触发不能证明自然触发正确 |
| `tdebug` | 显示额外调试信息 | 可帮助定位 TAG、州和省份 |
| `reload loc` | 重载本地化 | 不代表所有数据库都可安全热重载 |
| `reload focus` | 重载国策 | 最终仍要从新游戏验证 |
| `gui` | 检查 GUI 信息 | 可结合 sprite 名搜索源文件 |
| `nudge` | 地图工具入口 | 输出可能写入用户数据目录 |
| `observe` | 辅助长跑观察 | 观察者模式可能改变 AI 表现 |

来源：[Wiki Console commands](https://hoi4.paradoxwikis.com/Console_commands)，已保存 [离线正文](references/wiki/Console_commands.txt)。可用性会随版本、模式和键盘布局变化。本包没有把 CK3 等其他游戏的 `script_docs` 命令当作 HOI4 通用命令推荐。

## 4. 最小复现与运行验收

1. 保留出错时的日志和相关文件。
2. 将内容缩小为“一个入口 → 一个条件 → 一个效果”。
3. 检查当前作用域和引用对象，暂时减少无关分支。
4. 修复后测正向、反向、重复触发、存读档和正常启动。
5. 确认单独运行后，再逐个加入其他依赖模组复测。

**有意义的验收结果**是“指定国家在指定条件下得到指定效果，且相关新增错误消失”。编辑器没有红线、游戏能到主菜单、或截图看起来正常，都不足以覆盖完整行为。

## 5. 性能与版本迁移

性能建议属于工程实践：减少高频全局循环，优先限制作用对象，在需要时触发而不是无条件每小时遍历；长跑测试时记录固定机器、日期范围与配置。不要只因为功能很小就假设其检查频率没有成本。

每次游戏大版本更新：

- 记录新旧原版版本，对被覆盖的原版文件做差异比较。
- 重新核对删改接口、目录和数据结构，特别是地图、人物、装备、学说等。
- 重建编辑器 vanilla cache，确认规则集是否更新。
- 新开游戏测试；旧存档兼容性单独验证并明确说明。
- 验证后才更新 `supported_version`，并保留迁移说明。

官方开发日志展示了新版本会增加脚本功能并调整性能；旧视频只能提供思路，不能自动证明当前接口。[2023 Modding 日志](https://steamcommunity.com/games/394360/announcements/detail/3648531811786549063)、[2024 Performance and Modding 日志](https://steamcommunity.com/games/394360/announcements/detail/4445708897933590809)

## 6. 发布前清单

以下为项目验收建议，不是平台强制认证：

- [ ] 明确模组目标版本、依赖、DLC 条件、语言、冲突范围、是否需要新存档。
- [ ] 描述符和内容一致；发布包不含开发者机器的 `path`。
- [ ] 有意保留/更新正确的 `remote_file_id`；新作品不沿用他人 ID。
- [ ] namespace、对象 ID、本地化 key 和 sprite 引用检查通过。
- [ ] 本地化 BOM、文件名、首行语言一致；普通脚本编码符合要求。
- [ ] 原版基线与本模组日志已比对，新增相关错误已解释或修复。
- [ ] 正向、反向、重复触发、存读档、正常启动均有记录。
- [ ] 若声明联机兼容，两端用同一版本和模组组合实际验证 checksum 与运行。
- [ ] 若声明成就兼容，检查目标版本的 `checksum_manifest.txt` 和游戏内状态；不要从“只是小改动”推断。
- [ ] 用干净目录检查包内没有遗漏资源、个人绝对路径、缓存、日志和不需要的参考资料。
- [ ] 素材和借用代码的来源、署名与许可明确；公开 GitHub 仓库不自动意味着所有素材可再分发。
- [ ] 发布说明写清功能、安装顺序、依赖、已知问题、版本和反馈所需复现信息。

游戏 checksum 与文件改动的关系见 [Wiki Modding](https://hoi4.paradoxwikis.com/Modding)。平台的当前发布入口与条款应在实际发布时核对；本次只整理资料，没有创建或上传作品。

## 7. 工具边界

[CWTools Action](https://github.com/cwtools/cwtools-action) 可作为团队静态检查的候选工具，但应先查 README 中游戏支持、版本和配置参数，再试跑。CI 适合发现结构、引用和格式问题；游戏效果、地图正常加载、AI 表现和存档兼容仍需要游戏测试。

本次没有安装扩展、配置 CI 或运行下载来的第三方程序。保存的 CWT 是参考数据，不能当作游戏脚本直接加载。
